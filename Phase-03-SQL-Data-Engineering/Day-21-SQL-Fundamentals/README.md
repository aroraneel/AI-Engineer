# Day 21 — SQL Fundamentals: SELECT, WHERE, ORDER BY, GROUP BY, HAVING

**Topics:** SELECT, WHERE, ORDER BY, GROUP BY, HAVING — using SQLite via Python's `sqlite3` module

## What I Learned

- **SELECT** — chooses which columns to retrieve from a table. `SELECT *` gets all columns; `SELECT col1, col2` gets specific ones.
- **WHERE** — filters individual rows based on a condition, evaluated BEFORE any grouping happens.
- **ORDER BY** — sorts the final result set; `ASC` (default) for low-to-high, `DESC` for high-to-low.
- **GROUP BY** — groups rows sharing the same value in a column, almost always paired with an aggregate function (`COUNT()`, `AVG()`, `SUM()`, `MAX()`, `MIN()`). Same concept as Day 8's Pandas `groupby()`, different syntax.
- **HAVING** — filters groups AFTER aggregation has happened. This is the key distinction from WHERE: you can't filter on an aggregate result (like `AVG(salary)`) using WHERE, because at the point WHERE runs, that average hasn't been calculated yet.
- **Query execution order** (different from the order clauses are written): `FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY`. This directly explains why HAVING can reference aggregates and WHERE can't.
- **Running SQL via Python** — the standard pattern: write the query as a string, `cursor.execute(query)`, `cursor.fetchall()` to retrieve results, then `print()`. Reused identically across all 5 tasks.
- **Practical Git hygiene:** a `.db` file created by a script that fully regenerates its own data (DROP + CREATE + INSERT every run) doesn't need to be committed to Git — added `employees.db` to `.gitignore` since it's fully reproducible, unlike Day 3's `store.db` which was static input data.

## Mistakes I Made & Fixed

- Wrote raw SQL directly as Python code (`SELECT * FROM employees WHERE...`) without wrapping it in a string — Python doesn't parse SQL syntax natively; it needs to be a string passed to `cursor.execute()`.
- In Task 2, combined the WHERE condition into the ORDER BY clause instead of using them as separate clauses (`ORDER BY salary desc < 55000`), and had the comparison direction backwards (`<` instead of `>`).
- In Task 4, two typos broke the query: `GROPU BY` instead of `GROUP BY`, and `> 6000` instead of `> 60000` — missing a zero changed the entire meaning of the filter.
- In Task 5 (the hardest task, combining all 5 clauses), initially wrote the query missing `SELECT`/`FROM` entirely, used invalid placeholder-style references (`departments`, `result`) instead of the actual `COUNT(*)` expression needed in both HAVING and ORDER BY, and had the HAVING comparison direction backwards (`<=` instead of `>=`). Rebuilt it piece by piece, fixing one broken reference at a time.
- Discovered `employees.db` was being created at the repo root instead of inside the Day 21 folder — caused by VS Code running scripts from the workspace root directory rather than the file's own location. Resolved by choosing not to track the file at all (added to `.gitignore`), since it's fully regenerated by each script.
